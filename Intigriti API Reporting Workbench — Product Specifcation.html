API Reporting Workbench — Product Specification

1. Purpose

Build a lightweight, branded single-page application that lets employees or customers use an API key to quickly generate reports, charts, and data views from API data.

The goal is not to replace the platform UI. The goal is to create a flexible, local/self-serve reporting workbench that makes it easy to prototype new API-driven views without waiting for product development, internal data pulls, or custom one-off reporting.

This tool should help people answer questions like:

  • What changed in triage today?
  • How many submissions came in, moved forward, or were closed?
  • What is the current bounty budget position?
  • Which programs have noisy submission patterns?
  • What does a customer want to see that the platform does not yet expose?
  • Can we quickly prototype a report before deciding whether it belongs in the product?

2. Problem Statement

Customers sometimes need custom visibility into their programs that is not currently available in the platform UI. Internal teams can often access or assemble this data, but doing so creates manual dependency on CSMs, triage, product, or data teams.

In the meeting example, Customer-A asked for a daily triage in/out report. The platform did not expose exactly what she wanted, and internal reporting required asking someone else to generate the numbers. The API may already provide enough data to answer the request, but customers and CSMs need a practical interface for turning API data into useful reports.

This creates a gap:

  • Customers know what they want to measure.
  • The API may expose the underlying data.
  • Internal teams can help interpret requirements.
  • But there is no fast, low-friction tool for turning API access into reusable reports or charts.

3. Product Vision

Create an API Reporting Workbench: a static, browser-based single-page app that can be opened locally on a worker’s desktop browser (not hosted as a web server). To enable extended functionality, it could be developed using a web framework like Node which can be deployed locally.

A user provides their own API key, the app first validates the key (showing which programs the key has access to), asks the user to select which programs they want to interact with, then fetches available API data, and lets the user run predefined report modules.

The application should be easy for Claude Code or another coding agent to extend to create new report modules. A user should be able to say:

“Add a report that shows me daily triage movement for the last 14 days, grouped by status.”

…and the codebase should have a clean enough structure that a new report can be added quickly without rebuilding the whole app.

Report modules should be clearly separated so they can be delivered individually to the application’s users, and will be loaded dynamically based on what is available to the application at loading time (do not show blank placeholders for report modules that are not available to the user). Each module should also come with an example set of data and visualization, so the user can see what the report will produce before activating it to fetch/build/generate/display with live data.

The app should be capable of caching data in files on the local filesystem in a user-defined folder (and also loading from a user-defined folder). Each time the app fetches data, it should cache/save the data set locally; this will allow historical look-back and comparison over time. Each data chunk stored should be clearly labeled with a timestamp of when it was fetched. Make sure the user knows that this data could contain sensitive information such as vulnerability details.

Optionally, allow the user to encrypt the data cache on the filesystem using their API key as the encryption key using a symmetric encryption algorithm that is very strong. The user must be informed that the API key will be used for encryption. Allow the user to insert their own encryption key instead of using the API key. Warn them that this encryption may not protect the data if it is stolen.

Data loaded from the local cache should be immediately available to the report modules to visualize and process. If encrypted on the filesystem, the key must be provided before decrypting the data.

Offer a toggle (default to off) for the user to allow saving the API and encryption keys into the browser storage for ease of use. Warn that this is an insecure method for storing such sensitive keys.

Include buttons to explicitly test the API key and the encryption key.

Once entered and validated, the keys should not be visible on the page anymore. Keys should NEVER be visible in a printout of the application (like a print-to-pdf).

Future idea: Users would like to be able to drag report modules to be able to re-order them on the page.

Reports (modules) should be individually exportable as an image file, and also as a comma-separated-value (CSV) file of the data that is used to build the report. It would also be great if the tables or graphs were exportable as a slide format (like powerpoint or google slides) instead of being an image.

Widgets, functions, display components, etc should be build to be highly re-usable by other modules and areas of the application.

4. Primary Users

4.1 Internal users

Examples: Ryan, Chris, Customer Success, Sales Engineering, Product, Triage leadership.

Needs:

  • Generate customer-facing reports quickly.
  • Prototype customer-requested charts.
  • Validate whether API data can answer a request.
  • Avoid repeatedly asking product, data, or triage teams for manual exports.
  • Create screenshots or exports for customers.

4.2 Customer power users

Examples: program managers like Customer-A.

Needs:

  • Use their own API key.
  • Generate custom reports from their program data.
  • Avoid waiting on for every reporting request.
  • Export results for internal stakeholder reporting.
  • Understand program health, triage throughput, submission movement, and bounty spend.

4.3 Developers / AI coding agents

Examples: Claude Code, internal builders, technical CSMs.

Needs:

  • Simple architecture.
  • Clear API client layer.
  • Clear report-module pattern.
  • Easy way to add new reports, charts, filters, and data transformations.
  • Minimal deployment complexity.

5. Core Principles

  1. Client-side only
    The app should run entirely from the user’s local computer and should NOT require any remote webserver hosting (hosting may be done locally if required by the build structure).
  1. Bring your own API key
    The app must not ship with an API key. Users paste their own key at runtime.
  1. Do not persist secrets by default
    API keys should be stored in memory only unless the user explicitly opts into local browser storage.
  1. Fast iteration over polish
    The first version should prioritize useful reports and developer extensibility over perfect UX.
  1. No platform dependency
    The tool should not require product changes to be useful.
  1. Report modules should be composable
    Each report should be isolated enough that Claude Code can add, remove, or modify reports without touching unrelated code.
  1. Useful without AI, extensible with AI
    The app should include predefined reports, but the codebase should be structured so AI tools can generate new report modules.
  1. Re-usable components and utilities
    Widgets, functions, display components, etc should be build to be highly re-usable by other modules and areas of the application.

7. MVP User Flows

7.1 First-time launch

  1. User opens the app.
  1. App displays brief explanation and API key input.
  1. App warns that API data and cache files may contain sensitive vulnerability and program information.
  1. User pastes API key.
  1. User optionally sets API base URL.
  1. User optionally selects a local cache folder.
  1. User optionally enables cache encryption and chooses whether to use the API key or a separate encryption key.
  1. User optionally enables “Remember on this device” for API/encryption keys, with an explicit insecure-storage warning.
  1. User clicks Test key.
  1. App calls a safe validation endpoint.
  1. If successful, app hides the key, displays authenticated state, and lists available programs.
  1. If failed, app shows clear error and troubleshooting guidance.

7.2 Run a predefined report

  1. User selects a report, such as Daily Triage Movement.
  1. App shows a sample preview using bundled example data so the user can understand the report before running it live.
  1. App displays required parameters:
    • Program
    • Date range
    • Grouping
    • Optional filters
  1. User clicks Generate report.
  1. App checks whether relevant cached data is already available.
  1. App fetches missing or refreshed API data as needed.
  1. App saves each fetched data chunk to the selected local cache folder with a timestamped filename.
  1. App transforms live and/or cached data client-side.
  1. App displays:
    • Summary metrics
    • Table
    • Chart where appropriate
    • Raw JSON toggle
  1. User exports the report as CSV, JSON, image, or copied text summary.

7.3 Load and analyze cached data

  1. User selects a local cache folder.
  1. If files are encrypted, user provides the correct decryption key.
  1. App loads available cached datasets and displays their source, program, endpoint, and fetch timestamp.
  1. User selects one or more cached datasets.
  1. Report modules immediately become able to use that local data without making new API calls.
  1. User can compare current data to earlier cached snapshots where the report supports historical comparison.

7.4 Add a new report with Claude Code

  1. User opens the codebase in Claude Code.
  1. User asks Claude to add a report.
  1. Claude reads REPORT_MODULE_GUIDE.md.
  1. Claude creates a new report module file with bundled sample data and preview configuration.
  1. Claude registers it in the report registry or places it in the dynamically loaded modules directory.
  1. Report appears in the UI only if available and compatible.
  1. User tests it with sample data, cached data, and then live API data.

9. Functional Requirements

9.1 API key handling

  • App must provide a password-style input for the API key.
  • App must keep the key in memory by default.
  • App may offer “Remember on this device” using local storage, but it must be off by default.
  • App must provide a Clear key button.
  • App must provide an explicit Test API key button.
  • App must hide the API key after it has been entered and validated.
  • App must never log the API key to console.
  • App must never include the API key in exported reports.
  • App must never include the API key in print/PDF output.
  • App must never send the API key anywhere except the configured API base URL.
  • If local browser storage is enabled, the app must show an explicit warning that this is an insecure convenience feature.

9.1.1 Encryption key handling

  • App must allow the user to enable or disable cache encryption.
  • App must allow the user to use either the API key or a separate user-provided encryption key for cache encryption.
  • App must clearly inform the user when the API key is being used as the encryption key.
  • App must provide an explicit Test encryption key button.
  • App must hide the encryption key after entry/validation.
  • App must never log the encryption key to console.
  • App must never include the encryption key in exported reports or print/PDF output.
  • App must warn that encryption may not protect data if the local machine, browser profile, or key material is compromised.

9.2 API client

Create a dedicated API client module responsible for:

  • Base URL configuration.
  • Authentication header injection.
  • GET requests.
  • Pagination handling.
  • Rate-limit handling where possible.
  • Standard error normalization.
  • Safe request logging with secrets redacted.
  • Optional mock mode using local fixtures.
  • Returning normalized metadata for cache labeling, including endpoint, program, query parameters, and fetch timestamp.

The client should make it easy to add endpoint-specific helpers later.

9.3 Local data cache

The app should include a local cache manager responsible for:

  • Asking the user to select a cache folder where browser/runtime support allows.
  • Saving fetched API responses as timestamped data chunks.
  • Loading cached datasets from a user-selected folder.
  • Labeling cache files with source endpoint, program identifier, date range if known, and fetch timestamp.
  • Making cached data immediately available to report modules.
  • Supporting encrypted and unencrypted cache files.
  • Warning users before saving potentially sensitive vulnerability or program data.
  • Never saving API keys or encryption keys inside cache files.

Suggested cache filename format:

intigriti-cache__PROGRAM_OR_SCOPE__ENDPOINT_NAME__YYYY-MM-DDTHH-mm-ssZ.json

If encrypted:

intigriti-cache__PROGRAM_OR_SCOPE__ENDPOINT_NAME__YYYY-MM-DDTHH-mm-ssZ.enc

9.4 Report module structure

Each report should define:

  • id
  • title
  • description
  • category
  • Input parameter schema
  • Data requirements / API calls
  • Transform function
  • Output table columns
  • Chart configuration
  • Summary formatter
  • Export behavior
  • Sample dataset
  • Sample preview configuration
  • Cache compatibility declaration
  • Required API scopes or data shapes, if known
  • Availability checks so unavailable modules can be hidden rather than displayed as empty placeholders

Reports should not directly handle API key storage or global app state. They should receive an authenticated API client and user-selected parameters.

9.5 Dynamic module loading

  • Report modules should be individually deliverable.
  • App startup should discover available report modules.
  • The UI should show only modules that are present, compatible, and available to the current data/API context.
  • Each module should include a sample preview so users can see expected output before running the report.
  • The app should fail gracefully if a module is missing, malformed, or incompatible.

The app should include:

  • API key connection panel.
  • Encryption/cache settings panel.

9.8 Configuration

The app should support:

  • Default production API base URL.
  • Manual base URL override for staging/testing.
  • Mock mode for local development without real API access.
  • Local fixture files for sample responses.
  • User-selected local cache folder.
  • Cache encryption enabled/disabled setting.
  • Optional browser storage for keys, default off.

10. Non-Functional Requirements

10.1 Security

  • No backend required for MVP.
  • No API keys committed to source control.
  • No API keys stored unless user opts in.
  • Local storage key must be clearly named and easy to clear.
  • Redact secrets from logs and errors.
  • Prefer read-only endpoints in MVP.
  • Warn users that data visible in the tool depends on the permissions of their API key.

10.2 Privacy

  • Customer data should remain between the user’s browser and the API.
  • No analytics in MVP unless explicitly added later.
  • No third-party telemetry by default.
  • No customer data sent to AI services from inside the app.

10.3 Performance

  • App should handle at least thousands of submissions in browser memory.
  • Use pagination and loading states.
  • Avoid blocking UI during large transformations.
  • Consider virtualization if tables become large.

10.4 Maintainability

  • TypeScript preferred.
  • Clear separation between:
    • API client
    • Auth/key handling
    • Report definitions
    • Data transformation
    • UI components
    • Export utilities
  • Include mock data and example fixtures.
  • Include developer guide for adding reports.

13. CORS / Local Proxy Contingency

If the API does not support direct browser calls due to CORS, implement a local-only optional proxy.

Proxy requirements:

  • Node/Express or lightweight Vite dev proxy.
  • Runs locally.
  • Accepts requests from the SPA.
  • Adds the API key server-side only for that local session.
  • Does not persist API keys.
  • Does not log API keys.
  • Should be clearly marked as optional development/local mode, not a hosted production service.

If a proxy is needed for customer distribution, reassess the architecture because a hosted proxy would introduce security, privacy, authentication, and support responsibilities.

16. Acceptance Criteria

MVP is acceptable when:

  • User can open the app locally.
  • User can enter and clear an API key.
  • App can validate the key or clearly report that validation is unavailable.
  • User can run at least one report using mock data.
  • User can run at least one report against the live API once endpoint mappings are configured.
  • User can select a program if the API exposes programs.
  • User can configure date range.
  • User can view report results as summary cards, table, and chart.
  • User can export CSV and JSON.
  • API key is not persisted unless explicitly requested.
  • API key is not logged.
  • New report modules can be added without modifying core app logic.
  • README explains setup, running locally, mock mode, and live API mode.
